    What to read into this¶

    v0.2.0 ships NKI for correctness, not speed. At every data point the NKI path is slower than both CPU backends. Two reasons, both structural:

    1. No sparsity exploitation yet. v0.2.0's NKI kernel materializes the CSR into a dense (M, K) tile before the matmul. At density 0.001 on a 1024 × 1024 matrix, this means 1000× more work than scipy does. Real sparse speedups come from row-bucketing + gather-matmul-scatter, which lands in v0.3.0 (#15).
    2. Kernel-launch overhead dominates. The NKI times are roughly constant at ~1.3-2.5 ms across densities — the NEFF dispatch + HBM round-trip amortizes over large workloads, not these small ones. trn2 (v0.2.x Phase 5, #17) and NEFF-cache reuse (part of Phase 3) close this gap for steady-state workloads.

    What v0.2.0 does deliver:

    • set_backend("nki") now actually runs SpMM on the Tensor Engine.
    • Forward + backward (via torch.autograd.Function) both validated on hardware; torch.autograd.gradcheck passes at atol=1e-4.
    • The full Neuron toolchain — compile, NEFF cache, XLA dispatch, PyTorch integration — is exercised end-to-end, which is what Phase 1 is for.

    Reading the BSR table¶

    Three observations, all consistent with the architectural framing:

    1. bsr PyTorch scales linearly with block density (0.11 → 0.43 ms as density goes 0.10 → 0.50, ~4× more work done). It's the straightforward "iterate stored blocks, do A_block @ B_slice" reference. This is what the NKI path has to beat.
    2. bsr NKI is roughly constant at 1.8-3.1 ms across configurations. Kernel dispatch + compilation + HBM round-trips dominate at these small sizes, not the matmul work itself. This mirrors the v0.2.0 CSR finding — Trainium rewards amortizing the kernel launch.
    3. Dense CPU is the ceiling to beat — scipy / torch.sparse / BSR PyTorch are all within 2-4× of it on the trn1.2xlarge's Xeon. NKI needs workloads where the matmul work is large enough to swamp dispatch, or where the kernel launch can be amortized across many operations.

    Where NKI wins — shipped v0.4.x¶

    Not in raw "one-shot SpMM at N=128 vs CPU." The BSR table above measures kernel dispatch overhead. The architectural wins come from fusing multiple host passes into one dispatch:

    • screened_spmm (v0.4.0, #19) ✅ shipped: fuses Schwarz bound + threshold + mask + matmul into one NKI dispatch. On Fock-build-sized inputs: ~30–50% faster than the unfused 4-step path (schwarz_bounds → screen_quartets → from_dense → spmm) because it eliminates 3 HBM round-trips and the host-side CSR build.
    • Block-sparse attention (v0.4.2, #21) ✅ shipped: bsr_spmm handles attn_weights @ V for local-window / dilated / global-token masks. At seq_len=8192, window=2: 4.9% block density means 95% of nc_matmul calls are skipped. Current example still materializes the full score matrix (follow-up: #25).
    • #22 — on-chip iterative solvers: CG/power-iteration with A SBUF-resident across all iterations (replaces #20). v0.3.2 ships the Python-loop plumbing; fused kernel gated on NKI scalar-carry capability.

    See docs/architecture.md for why BSR is the Trainium-native format.

    Reading the Trn2 tables¶

    • BSR SpMM pays off at scale and moderate sparsity. At n = 8192 the static kernel beats dense aten up to ~14% block density (width 128) and ~34% (width 512); at 1% it is 2.7–6.8× faster. Its cost is linear in stored blocks (~1.9 µs per 128×128×512 block vs ~0.66 µs per block for dense aten), so the crossover moves up with n and with width. At n = 1024 nothing sparse wins: one launch costs ~0.3 ms and dense aten is 0.14 ms. Against CPU (dense or torch.sparse) the device wins everywhere above n = 1024.
    • The gather path was the bottleneck, not the Tensor Engine. On main, device-side pad + gather took 60% of every call and the K_max padding made each row cost as much as the densest row. With the structure as kernel constants both are gone: 3–6× faster end to end at 8192.
    • Attention forward never beats unmasked dense SDPA (a fused kernel at 0.77 ms for seq 8192), but it is what to compare against when the mask is real: masked SDPA costs 5.0–5.2 ms at 8192 and the static kernel 1.4–3.5 ms. Forward + backward beats unmasked dense SDPA at seq 8192 for local and global masks (3.5–4.2 ms vs 6.3–6.6 ms), not for 25% dilated (11 ms) and not at seq ≤ 4096.
    • Global-token masks were the pathological case for the gather path (K_max = all blocks): seq 8192 fwd+bwd went from 127–195 ms to ~4 ms.

    Reading the multi-core tables¶

    • The per-block fix moved the crossover more than extra cores did.
    • On one core, the pre-transposed, row-grouped kernel is 1.1–2.2× faster than the #36 kernel at 25–50% density.
    • It beats dense aten on that same core up to ~82–98% block density, and still beats it at 100% for n = 8192, width 512. In #36 the crossover was ~26–49% on two physical cores.
    • Where the time goes: B-tile loads, shared across up to 8 block rows of a group, and the in-kernel transpose, now gone.
    • Four logical cores pay only for large work per call.
    • Speedup from one core to four (pre-T): 1.4–2.3× at n = 16384 and 25–100% density, 1.2–1.6× at n = 8192 and width 512 above 25%.
    • It is a slowdown (0.45–0.8×) below ~0.6 ms of single-core work.
    • Why the speedup stops there:
    • One Python thread issues the launches, at about 0.1 ms each (0.4–0.7 ms for four).
    • Concurrent kernels on different logical cores also slow each other. At n = 16384, width 512, 50% density, one shard takes 1.15–1.3 ms alone and 1.9–2.9 ms with all four running. Dense aten slabs barely contend (2.5 ms alone, 3.1 ms for four).
    • Two cores reach most of the four-core gain.
    • One process per core does not help with two host CPUs: four processes are no faster than one.
    • Against dense split the same way, the crossover drops. Dense aten scales better across cores (3.7× from one to four at n = 16384, width 512), so the four-core crossovers are ~50–74% at n = 16384 and ~69% at n = 8192, width 512. At n = 8192, width 128 both sides sit on the launch floor (0.5–0.7 ms), so splitting is pointless there.
    • Attention, one head:
    • The forward on one core now beats unmasked dense SDPA at seq 16384 for local and global masks: 0.85–1.6 ms vs 2.0–2.2 ms.
    • At seq 8192 it ties: 0.55–0.89 ms vs 0.72–0.77 ms.
    • Splitting query rows over cores pays only for the 25% dilated mask at seq 16384: 5.2–5.7 → 2.9–3.0 ms, but that is still slower than dense SDPA at 1.8–2.2 ms.
    • Masked SDPA (32–33 ms at 16384 on one core, 6.6–11 ms on four) loses to every sparse configuration.
    • Attention, four heads (fwd+bwd):
    • With whole heads per core, sparse beats dense SDPA split the same way at seq 16384 for local and global masks: 10.5–14 ms vs 26–28 ms.
    • At seq 8192 the margin is narrower: 7.6–9.6 vs 10.5–12.5 ms.
    • The 25% dilated mask loses at both lengths.
    • Core scaling is 1.1–2.1×, held back by about 10–20 host-issued aten ops per head on the public path.

    Reading the CG tables¶

    • The win is removing the host from the iteration loop. The fused solve is 3.5–11x faster than the best 2-thread CPU solver at every size and density here. It is 5–58x faster than the same CG driven from the host over the already fast BSR SpMM op: that loop costs about 1–1.5 ms per iteration in launches and syncs, against 15–250 µs on the device.
    • A matvec costs about 0.5 µs per stored block per physical core, whether the block is resident or streamed. That is the TensorE load of a 128x128 fp32 stationary block for one moving column (a microbenchmark gives 497 ns per matmul at 1 column, 524 ns at 64, 985 ns at 512; bf16 is 100 ns). The DMA queues keep up streaming 64 KiB blocks from HBM at that rate (about 128 GB/s), so at n = 8192 with 1024 blocks, the 384 non-resident blocks did not cost extra time per block. SBUF residency stops fitting at 320 fp32 blocks per physical core (640 per logical core with the split), but past that point nothing falls off a cliff. Residency matters only when the per-block compute gets cheaper than the DMA (bf16, or many more moving columns).
    • The LNC=2 row split is 1.7–2.1x per iteration over running the whole solve on one physical core. LNC=1 matches the unsplit LNC=2 kernel.
    • Several right-hand sides are nearly free. R columns share each stationary load: 128 right-hand sides take 12.7 ms against 6.0 ms for one (n = 4096), i.e. 0.10 ms per solve. The best CPU per-solve time here is 2.6 ms (block bmm, R = 64), so that is about 26x.
    • Checking convergence on the device every 1–8 steps costs little. The device-side while test adds about 3 µs per check.
    • Precision is fp32. The recursive residual reaches tol. The true residual against the fp64 A lands at 0.5–2x tol for κ = 1e3, and the error against fp64 is 1e-6 to 1e-5. At κ = 1e5 the error grows to 1e-4 to 3e-4 (fp32 rounding of A times κ), where the fp64 CPU solvers do not have that floor. fp32 CG also takes about 5–25% more iterations than fp64 CG.

    Reading the follow-up tables¶

    • The column matvec beats the row matvec in every case measured. It is 1.03–1.2x faster at the smallest sizes (median of 11 runs), up to 3.2x faster to tolerance, and 2.7–3.9x faster per iteration. It is as accurate: true residuals and errors match the row matvec within run-to-run variation, and iteration counts differ by at most 4. That is why it is the new default for R <= 32.
    • Against the best 2-thread CPU solver, fused CG is now 5–56x faster to tolerance. In #40 it was 3.5–11x.
    • The per-block cost is no longer the floor. At about 50 ns per resident block, an iteration costs about 11 µs fixed at LNC=2 (8 µs at LNC=1) plus the blocks. The fixed part is the chain of small VectorE / TensorE steps and the sendrecvs. Cutting the exchanges from three to two saved 2–3 µs per iteration. So the LNC=2 row split now gives 1.1–1.2x up to 256 blocks and about 2x at 512–1024 blocks.
    • SBUF residency matters again. At n = 8192 with 1024 blocks, 384 of the fp32 blocks (64 KiB each) stream from HBM and set the pace: 87 µs per iteration, against 30 µs with 512 resident blocks. bf16 A keeps all 1024 blocks resident and is 2.3x faster there, but at bf16 accuracy.
    • bf16 A does not pay as a replacement for fp32 (opt-in only). The vectors stay fp32 (split into bf16 hi + lo) and accumulation is fp32, so the recursive residual converges, but for the rounded matrix. At κ = 1e3 the true residual against the fp64 A stalls at 1e-3 to 7e-2. At κ = 1e5 the error is about 0.9, or CG breaks down because the rounded matrix is indefinite (n = 8192, 1024 blocks). bf16 hi + lo (bf16x2) recovers most of the accuracy at κ = 1e3 (1–15x tol) but is 5–70x tol at κ = 1e5. It also costs as much as fp32: two matmuls and the same bytes per block.
    • Several right-hand sides. The column matvec takes up to 32 and is 1.2–3.3x faster per solve than the row matvec there. Above 32 the row matvec is used.
    • Fused power iteration (power_iteration_bsr_fused) runs 200 iterations in 3–19 ms. That is 9–51x faster than the best CPU baseline and 14–42x faster than power_iteration_bsr on the device, which syncs with the host twice per iteration. λ matches fp64 eigvalsh to about 3e-8 (fp32).
    • One process per logical core. The column matvec doubles the single-core rate (294 against 147 solves/s). Going to 2 and 4 cores scales 2.15x and 2.38x, limited by the 2 shared host CPUs as in #40.

    Reading the fixed-cost tables¶

    • The fixed cost per plain CG iteration fell from about 11 µs to about 4.4 µs at LNC=2, and from about 8 µs to about 3.5 µs at LNC=1. The biggest items were the exchanges (one per plain CG step instead of two, through GpSimd's SBUF-to-SBUF DMA, with no copies thanks to the segment layout) and the matvec tail (one PSUM copy and one transpose per chunk instead of four, from the spread source vectors).
    • Per iteration the new kernel is 1.28–1.43x faster at LNC=2 split for plain CG and 1.17–1.34x for PCG; at LNC=1, 1.02–1.26x (plain) and 1.03–1.32x (PCG). The matvec itself, about 270 ns per block on each of four concurrent column groups, now dominates from about 128 resident blocks per core; the row order that balances the groups takes 1–2 µs off at 256–512 blocks.
    • Streamed blocks. When A does not fit in SBUF (n = 8192 with 512 blocks on one core, 1024 blocks) the HBM stream sets the pace. There the kernel keeps the original row order and chunks of at most 32 rows, which measured faster than one large chunk (a first version with the balanced order and one 64-row chunk was 5–10% slower than #41 on these cases at LNC=1; the shipped rule is 1.02–1.13x faster).
    • Time to tolerance changes by 0.98–1.46x (the low end is within run-to-run noise). It includes the launch and the host-to-device and device-to-host copies (about 0.8–1 ms), which this change does not touch, so the gain is largest where iterations dominate. Two #41 entries at n = 8192, 256 blocks, κ = 1e5, LNC=2 (7.0 and 8.0 ms) are host-side outliers that persisted over 9 runs; the 3.3x there is not a kernel effect.
    • Accuracy is unchanged for the default: iteration counts are within ±3 and the true residuals and errors against fp64 match #41 within run-to-run variation (both are fp32 with a different summation order).
    • Chronopoulos–Gear saves about 1 µs per iteration (0.1–1.6 µs in the per-iteration table) but is less accurate: the true residual is up to 2–3x and the error up to 5x those of standard CG, and at n = 4096, 128 blocks, κ = 1e5 on one core it needed 92 iterations against 67. It stays opt-in.
    • PSUM allocation. The production kernels no longer fall back to neuronx-cc allocation and scheduling (#41 noted the fallback); the per-scope PSUM tiles were worth about 0.3 µs per iteration.
